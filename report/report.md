## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

本章实验围绕虚拟内存环境的完善与内核线程管理展开，核心主线是：先准备可靠的内存映射环境，再创建和初始化内核线程，最后通过调度与上下文切换让线程真正运行起来。

前面的实验已经解决了物理页的分配和基本地址映射问题，但内核仍然只有一条执行流。本实验进一步解决“如何描述多个执行实体、如何为它们准备运行现场，以及如何让它们轮流使用 CPU”的问题，使系统逐步具备多线程并发运行能力。

其中，虚拟内存部分采用预映射方式，为线程运行及后续地址空间管理提供基础，不涉及按需分配、缺页处理或页面置换。线程管理部分则使用统一的进程控制块描述内核线程。各内核线程共享内核地址空间，但分别拥有自己的内核栈和执行上下文，因此能够独立保存运行状态并参与调度。

### 2.2 功能的逐步实现

1.完善虚拟内存页操作，为线程运行提供可靠的内存基础。

在已有多级页表机制上，实现 page_insert() 和 page_remove()，完成虚拟地址与物理页之间映射的建立、更新和撤销。同时正确维护物理页引用计数，并使相关 TLB 缓存失效，保证页表内容与实际地址转换结果一致。

首先实现这一部分，是因为线程执行代码、访问数据和使用内核栈，都依赖正确的内存映射。只有底层内存管理可靠，后续线程创建和运行才有稳定基础。

2.初始化线程控制块和管理结构，使执行流能够被内核统一管理。

通过 alloc_proc() 分配并初始化进程控制块，用于保存线程状态、PID、内核栈、上下文和地址空间信息等。通过 proc_init() 初始化进程链表等全局结构，将当前执行流组织为 idleproc，并设置 current，明确当前正在运行的线程。

这一阶段解决的是“如何描述和管理线程”的问题。只有先建立统一的线程管理结构，后续才能登记新线程、查找线程，并根据线程状态进行调度。

3.完成内核线程创建和首次运行现场的构造，使新线程具备执行条件。

通过 kernel_thread() 组织线程入口函数和参数，再由 do_fork() 完成控制块分配、内核栈分配、地址空间处理、PID 分配和线程登记等工作。copy_thread() 负责设置新线程的中断帧和上下文，使其第一次获得 CPU 时能够进入指定函数。资源准备完成后，再将线程置为可运行状态，并在初始化过程中创建 initproc。

这一部分必须在调度之前完成，因为新线程尚未实际运行，没有可以直接恢复的历史现场，必须提前构造首次执行所需的状态。本实验中的 copy_mm() 保留地址空间处理接口，内核线程仍然共享内核地址空间，不进行独立用户地址空间的复制。

4.实现线程调度和上下文切换，让线程真正获得 CPU。

cpu_idle() 在空闲循环中检查是否需要调度；schedule() 从线程链表中选择可运行线程，没有合适对象时选择 idleproc；proc_run() 更新 current 并完成必要的页表切换；switch_to() 保存旧线程的寄存器上下文，恢复新线程的上下文，使 CPU 转向新线程继续执行。切换关键区域需要保存中断状态并关闭中断，完成后恢复原状态，避免切换过程被中断打断而造成状态不一致。

最后实现这一部分，是因为调度既依赖已经建立的线程管理结构，也依赖准备完整的内核栈和执行现场。完成后，initproc 才能从 idleproc 手中接管 CPU，整个实验便形成“准备内存环境、创建线程、登记为可运行、选择线程、切换执行”的完整运行流程。

#### 模块功能描述

**需要实现/修改的函数：**

```c
// 列出本模块涉及的所有函数签名
int page_insert(pde_t *pgdir, struct Page *page, uintptr_t la, uint32_t perm);
void page_remove(pde_t *pgdir, uintptr_t la);
```

**功能说明：**

本模块在现有多级页表框架上，实现虚拟地址与物理页之间映射关系的建立、更新和删除，为后续地址空间管理及内核线程运行提供基础。

本模块需要保持以下三者的一致性：

页表项内容： 正确记录物理页号、有效位和访问权限。
物理页引用计数： 准确反映通过页表映射引用该物理页的数量。
TLB 状态： 映射变化后使相关缓存翻译失效，避免继续使用旧的地址转换结果。
主要处理场景如下：

指定虚拟地址尚未映射时，建立新的映射。
指定虚拟地址已经映射到同一物理页时，更新权限，并保持引用计数不变。
指定虚拟地址已经映射到另一物理页时，撤销旧映射并建立新映射；旧页引用计数归零时释放旧页。
同一物理页映射到多个虚拟地址时，分别维护各映射对应的引用计数。
删除有效映射时，清除页表项、刷新 TLB，并减少物理页引用计数。
删除不存在的映射或重复删除时，安静返回，不创建页表或额外修改资源状态。
创建中间页表失败时，返回 -E_NO_MEM，回滚本次调用新建但未完成映射所占用的中间页表，保留已有映射和已有页表。
本模块与其他模块的交互关系如下：

使用 get_pte() 查找或创建目标页表项。
使用 pte_create() 构造包含物理页号、有效位和权限的页表项。
使用 pte2page()、pde2page() 和页引用计数接口管理物理页。
使用 free_page() 回收引用计数归零的页。
使用 tlb_invalidate() 使对应虚拟地址的缓存翻译失效。
为现有页表自检、静态内核映射检查及后续地址空间相关功能提供支持。
本次仅在 kern/mm/pmm.c 的功能模块一占位处实现上述两个函数，未修改其他成员负责的线程创建、调度代码或官方测试。

问题1：同一物理页重映射可能导致误释放。

**功能说明：**

1. 该模块在整个系统中的作用：进程调度模块负责将 CPU 分配给已经就绪的内核线程，使系统从“能够创建线程”进一步具备“能够执行和切换线程”的能力。它完成调度请求检测、可运行线程选择、页表切换和寄存器上下文保存恢复，使 initproc 能够从 idleproc 手中接管 CPU，并支持线程以后恢复执行。

challenge:1. 如何实现中断的关闭与恢复？
local_intr_save(intr_flag) 检查 sstatus 的 SIE 位，保存原来的中断状态，并在中断开启时将其关闭。local_intr_restore(intr_flag) 根据保存的状态决定是否重新开启中断。因此，它能恢复原状态并支持嵌套使用，保护调度和上下文切换等关键操作。
2. 不同分页模式如何工作？
Sv32、Sv39、Sv48 都通过虚拟地址中的索引逐级查找页表，最终得到物理页号，再结合页内偏移形成物理地址。三者分别采用两级、三级和四级页表；Sv32 每级索引占 10 位，Sv39、Sv48 每级占 9 位，页内偏移均为 12 位。本实验使用 Sv39，地址空间更大的分页模式通常需要更多层页表。
3. get_pte() 的两段代码为什么相似？
两段代码分别通过 PDX1 和 PDX0 处理不同层级，执行的都是“检查页表项是否有效，必要时分配、清零并挂接下一级页表”。由于多级页表各中间层的结构和处理方式相同，代码形式相似，最后通过 PTX 定位末级页表项。
4. 是否应该拆分查找和分配功能？
当前设计适合本实验：create 为 0 时只查找，为 1 时允许分配，能够复用遍历逻辑。但函数副作用不够直观，而且当前代码在后一级分配失败时不会回滚先前创建的页表。后续可以拆分只读查找和允许创建的对外接口，内部共用遍历逻辑，并完善失败清理。

## 六、实验总结与收获

### 对操作系统的理解

1. 本实验的重要知识点及其与 OS 原理的联系

进程控制块与执行实体管理。OS 原理中，进程控制块用于记录进程状态、资源和执行现场。本实验使用 struct proc_struct 统一管理内核线程，通过 state、pid、context、kstack 等字段描述线程。与具有独立用户地址空间的进程不同，本实验中的内核线程共享内核地址空间，但各自拥有独立的内核栈和上下文。

线程状态与调度。OS 原理通常区分就绪态、运行态和阻塞态。本实验将就绪与运行统一表示为 PROC_RUNNABLE，通过 current 标识实际运行的线程。schedule() 从当前线程的后继位置开始循环选择可运行线程，没有合适目标时回退到 idleproc。这体现了轮转选择的思想，但尚未实现完整的时间片管理。

上下文切换与 CPU 虚拟化。多个线程轮流使用 CPU，需要保存旧线程现场并恢复目标线程现场。本实验通过 struct context 和 switch_to() 保存、恢复 ra、sp、s0 至 s11。由于切换发生在正常函数调用边界，可以利用调用约定处理其他需要保留的值，因此不必在 context 中保存全部寄存器。

临界区与中断保护。线程切换涉及 current、页表和寄存器现场的协同更新，中途被中断可能造成状态不一致。本实验使用 local_intr_save() 和 local_intr_restore() 保存并恢复中断状态，保护单核环境中的切换过程。这体现了临界区保护思想，但关闭本地中断不能直接解决多核之间的并发访问问题。

分页机制与地址转换。OS 原理通过页表建立虚拟地址到物理地址的映射。本实验使用 Sv39 三级页表，通过 get_pte()、page_insert()、page_remove() 等接口维护映射，并通过 satp 指定根页表。VMA 描述地址区域的逻辑范围和属性，页表记录实际映射，二者承担不同职责。当前内核线程共享页表，因此切换线程通常不会改变实际地址空间。

TLB 与映射一致性。TLB 缓存地址转换结果和权限，能够减少页表查询开销。修改页表或切换根页表后，需要使用 sfence.vma 处理旧转换记录，保证后续访问与页表一致。TLB 未命中只表示需要查询页表，并不等同于缺页异常。

2. OS 原理中重要但本实验尚未覆盖的知识点

用户进程与权限隔离。本实验主要运行内核线程，尚未完整实现独立用户地址空间、用户程序加载和系统调用机制。

按需分页与页面置换。本实验采用预映射方式，尚未实现访问时分配页面、缺页处理以及页面换入换出。

完整的调度机制。当前实现没有覆盖优先级、多级反馈队列、时间片分配和调度公平性等内容。

完整的进程生命周期。当前 do_exit() 仍为占位实现，尚未完成退出资源回收、父进程等待和僵尸进程清理。

### AI 协作开发的经验

本次实验中，我们将 AI 作为需要复核的开发伙伴，在理解线程状态、调用约定和页表机制的基础上，由我们明确任务边界并把关实现质量，让 AI 辅助完成代码编写、解释和问题定位。

任务描述应围绕完整能力展开。调度功能由 cpu_idle()、schedule()、proc_run() 和 switch_to() 协同完成，因此提示词需要同时说明线程选择、状态更新、页表安装和寄存器恢复之间的关系，避免只要求补全某个函数。

AI 输出必须与真实工程核对。例如，Sv32 遗留的 lsatp() 不能直接用于 Sv39；汇编存取偏移必须与 struct context 一致；内存管理器的声明、定义和引用名称必须匹配。这些细节需要结合源码检查，不能仅凭生成代码看起来合理就接受。

验证应区分源码检查、编译和实际运行。我们通过编译日志定位未定义宏和链接符号问题，再通过 make grade 检查基本功能。最终 PMM、Process Create、Schedule 三项测试全部通过，总分为 30/30，说明现有测试覆盖的功能正常，但不代表所有边界场景和中断时序都已验证。

通过这次协作，我们认识到，AI 可以提高实现与排错效率，但专业判断、测试设计和结果解释仍由开发者负责。只有能够解释关键代码，并用实际证据验证其行为，才能真正掌握实验内容。
